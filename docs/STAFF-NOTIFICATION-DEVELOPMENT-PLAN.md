## 1. 執行方式

主規格決定功能行為，本計畫只安排順序與交付邊界。若實際程式已由其他任務前進，先比對實作、更新進度，不覆寫別人的改動，也不重做已滿足的項目。

採用 15 段：S00–S14。S00 是基線與契約盤點，其餘各有可獨立建置或檢查的交付物。最簡單的執行順序是照編號進行；每段開工前只需讀主規格相關章節、進度紀錄及本段入口。

不以未經量測的 token 數字保證某段一定能完成。若本段比預期大，可在不改變完成定義的情況下拆成 Sxx-a、Sxx-b，把接口與停點寫入進度；父段在全部子段完成前保持進行中。不要為了趕在額度結束前把未完成項目標為完成。

### 每段固定流程

1. 讀取所有適用 AGENTS.md；Web 程式變更前另讀 Web docs/coding-standards.md。
2. 讀進度檔「目前接續點」；若有進行中階段，優先恢復它，不直接開始下一編號。
3. 分別查 API、Web 的 HEAD、branch、git status；根工作區不代替兩個 repository 的狀態。
4. 讀本段相關規格與必要程式；在進度檔記錄開始狀態、基準 HEAD、計畫修改範圍。
5. 完成本段，保持既有功能可用，尚未完成的能力不對外宣告。
6. 依第 4 節驗證，記錄命令、結果及未執行原因；編譯通過不代表業務案例已測試通過。
7. 更新進度與交接，列出最小可接續動作。所有修改必須已落地檔案；不要只保存在回答或記憶體。
8. 本段結束後停止，回報實際狀態與下一段。不自動開始新任務、不自動發布。

### 模型與工作區

由使用者在下一次執行時選擇 5.6 Luna；本計畫不建立或切換任務。新任務需指向同一個工作區，或使用明確移交的 checkout。若以新 worktree 接續，必須先確認前段尚未提交檔案與進度檔已帶入；只有 HEAD 相同不足以代表工作相同。

進度檔可保存未提交的工作，不要求為了交接自動提交。若已獲准提交，只提交本段相關檔案並分別記錄 API／Web commit。不要以 git add . 收入其他任務內容。

## 3. 分段任務卡

### S00｜重新核對基線與接口

必讀：主規格第 2、8、10 節；兩個 repository 的 AGENTS；現有通知、音效與菜單 migration。

工作：

- 確认主規格記錄的 HEAD 與目前差異；列出已實作／部分實作／尚未實作。
- 固定 rule schemaVersion、ruleRevision、fingerprint、sourceType、payloadVersion、capabilities 與錯誤碼的命名及 JSON 例子。
- 為舊兩類規則、純指名、營業提醒各記錄最小 payload；定義沒有 orderId 時 action 如何表達。
- 列出資料遷移依賴與各段將新增的欄位／表，執行時再分配不衝突的 migration 編號。
- 列出通知啟用 flag、解析器、系統音檔、DB 套用狀態的已知／未知，不讀出秘密設定內容。

停點：進度檔的「契約決策」與「基線」可供下一段直接採用；本段不修改執行程式。

完成判定：不存在要求下一段自行猜測的核心資料格式；Someone／ALL 與香檳塔不再重開產品討論。

### S01｜相容 DTO 與非訂單來源

必讀：主規格第 2.4（4、9）、8 節。

入口：API MenuNotifications.cs、MenuNotificationsController.cs；Web notifications/types.ts。

工作：

- 新增版本化 payload reader／writer，舊 payload 的來源預設為 order_submitted。
- 保留舊 orderId；新來源允許 null，提供 sourceType/sourceId/action，未知版本給明確處理。
- 修改依來源失效判斷，不能對所有通知都查訂單；舊提交來源沿用現行取消／完成失效。
- capabilities 舊欄位保留；擴充可協商能力，未完成項目維持關閉。
- 只做相容型別與必要最小 renderer 防護，不重做整個通知中心。

完成判定：舊規則／delivery 不需重建就能讀；非訂單訊息不被失效 SQL 清掉，不出現 null 訂單連結。相關專案可建置。

### S02｜規則條件、去重與版本

必讀：主規格第 2.1、3.2、4、8.2 節。

入口：MenuNotifications.SaveAsync、設定 DTO／JSON；必要 migration。

工作：

- 納入八類規則 schema、targetMode/targetStaffId、offsetMinutes、20 條容量與排序。
- self 與指定自己採一致 fingerprint；不同 N／不同對象可並存，完全相同條件拒絕。
- 保留整組 expectedRevision 原子儲存；另由伺服器管理逐規則 revision，不信任客戶端指定它。
- 記錄觸發條件與呈現設定變更的版本語意；只改 B 不得讓 A 的執行版本失效。
- 舊客戶端可儲存舊資料，但不得覆蓋含新欄位的設定。新規則 runtime 尚未完成時不宣告可啟用。
- 維持 sound ownership 與廣播權限驗證。

完成判定：條件、版本與衝突行為完整；N=0 不被當成空值；既有 RuleType 唯一限制已由 fingerprint 取代。API 可建置。

### S03｜可靠派送與命中快照

必讀：主規格第 2.4（3）、7.1、7.2、8.1 節。

入口：EnqueueAsync／DispatchOneAsync、MenuNotificationWorker、outbox migration。

工作：

- 保存命中規則版本／條件快照；派送前僅因該條停用、刪除、觸發條件已改或來源失效取消。
- 不因無關規則儲存、排序或整組 revision 改變而吞掉待發事件。呈現設定採本段已記錄的明確快照規則。
- 加 attempts／nextAttemptAt／錯誤／隔離狀態；失敗交易外記錄重試，不讓壞資料永遠堵住佇列。
- 沿用交易 SKIP LOCKED 與 SOURCE_KEY 去重，禁止另外建通知平行系統。
- 建立來源匹配合併與優先序 helper；通知／delivery 變更集中到可供 S11 接 change log 的寫入入口。
- 保持取消、完成、帳號停用等判斷，新增 audit 必要項。

完成判定：一筆交易失敗不會通知；重派不重複建立；改 B 不影響 A；失敗事件可隔離後繼續其他事件。重試行為有紀錄，不只 catch log。

### S04｜新指名單

必讀：主規格第 2.1、2.2、4（規則 1、2、8）、7.2 節。

入口：OrderingRepository.CreateOrderAsync、EnqueueAsync、匹配 helper。

工作：

- 移除「沒有 menu item 就整個 return」的範圍限制，依個別規則匹配來源。
- 純指名匹配 self/staff/all；純小費／純房間單不誤觸點餐。
- 混合點餐／指名／香檳塔仍沿用 order:{id}:submitted，合併為每帳號一筆。
- 香檳塔沿用 MenuSnapshotJson，不重讀當前菜單來判歷史事件。
- 新提交規則的能力標記只在完整路徑可用後開放。

完成判定：規則 1、2、8 的接單來源與受眾一致，混合單沒有第二份提交 outbox；程式可建置。

### S05｜指名時間排程

必讀：主規格第 4.1、4.2、7.1、7.2 節。

入口：指名確認／改期／縮短／取消交易；新增 schedule 表與背景服務。

工作：

- 建立 dueAt、expiresAt、scheduleRevision、ruleRevision 及唯一 scheduleKey。
- 確認成立後建立規則 3–5；改期／縮短／取消令舊任務失效，派送前再核對。
- 使用有效服務結束，不用 buffer ends；正常完成後仍可有規則 5，取消／作廢不可。
- 同時處理 N=0、15 分鐘窗口、過去觸發不補播、worker 恢復；不同 N 不合併。
- 新規則儲存後須安排未來既有有效時段的未來觸發，不追溯播放過去時點。
- schedule 與 outbox 交接保持冪等，排程服務不得改訂單業務狀態。

完成判定：規則 3–5 可排程並重排；所有改期入口已列出且串接。若太大，拆 S05-a「資料／建立」、S05-b「異動／派送」，父段不得提前完成。

### S06｜營業時間排程

必讀：主規格第 4.1、4.2（營業與跨日）。

入口：有效營業 context、ProjectedCloseAt 異動、S05 排程服務。

工作：

- 接入規則 6、7，共用既有 clock／營業日期解析。
- 無可靠營業計畫時不生提醒；跨日歸屬正確；營業中關店以 ProjectedCloseAt 優先。
- 預定時間變更重排，提前實際開／關店取消無意義任務。
- 為每日營業計畫尚無 BUSINESS_PERIODS row 的情況定義穩定 schedule identity。
- 保持 business override 的現有語意，不修改牆上時鐘。

完成判定：規則 6、7 不依瀏覽器計時；22:00–隔日02:00 等案例有可核對的 dueAt。API 可建置。

### S07｜個人規則編輯與音效按鈕

必讀：主規格第 3、4、6；Web coding standards。

入口：AdminNotificationCenter.tsx、types.ts、api.ts；依現有模組邊界拆 TSX 元件。

工作：

- 通用「＋新增規則」、複製、目標、N、20 條容量、上移／下移與拖曳。
- 原子儲存、未存草稿離頁提醒、409 不丟草稿；依 capabilities 顯示已支援種類。
- Bell／BellRing、名稱與 aria-label；音效選擇、試聽／停止，none/toast/sticky 獨立聲音設定。
- 規則預覽只對本人且不產生正式事件；如需 /test，在本段一併完成小範圍 API。
- 維持廣播頁既有功能，不順便完成後段全部廣播 UI。

完成判定：八種個人規則完整可編輯；尚未啟用能力不誤導使用者；Web build／允許靜態檢查通過。非一般 E2E 例行執行點。

### S08｜廣播管理與手動發送

必讀：主規格第 5、7.2、8。

入口：broadcast RULES_JSON、controller、廣播 UI；通用來源 dispatcher。

工作：

- 保留舊廣播 owner／id；新增受眾、priority、有效期與模板設定，預設全員含無 staff 管理者。
- 按發送時快照 account ids；同一事件合併規則，強制廣播只選系統音效。
- 手動 send 使用 idempotency key，純文字內容與受控 action。
- 來源失效判斷支援手動／營業事件，不強制 orderId。
- 先完成一般／高優先，requiresAck 功能在 S09 完成前不可對外啟用。
- UI 提供對象與有效期檢視，測試不發全員。

完成判定：手動重按不重複發送，舊兩種廣播設定仍有效，修改範圍與權限均由後端驗證。

### S09｜已知道、撤回與緊急確認

必讀：主規格第 3.3、5、7.2。

工作：

- delivery acknowledgement、廣播實例撤回、管理者 receipts；read 與 ack 分開。
- 合併來源須可追查與撤回；必要時引入 MATCHES，不能撤回一筆就把另一未撤回來源清掉。
- 緊急 Modal 依序呈現、焦點處理、到期／撤回解除；不改訂單狀態。
- 首次登入恢復有效未確認廣播，不套用個人歷史 baseline 跳過。
- receipts 區分未讀／已讀／已確認／到期未確認。

完成判定：確認冪等、不能代他人確認；全部已讀不等於 ack；撤回後不再阻擋，所有操作有 audit。變更先能透過現有 inbox 同步，不依賴 S11 才可完成。

### S10｜重複提醒與堆積

必讀：主規格第 5.2、7.2。

工作：

- occurrenceNo、至少 1 分鐘、最多 5 次；重複更新原卡，呈現 id 帶 occurrence。
- ack、取消／解除、過期或撤回停止相關重複。
- 固定待處理訂單集合，K／M 門檻與 episode；下降後重置。
- 備妥來源命中追蹤，混合廣播重複不遺失其他來源確認需求。
- 發布前模板預設與系統音效就緒依主規格處理，不自動替正式全店開啟。

完成判定：不因每輪掃描新建 episode；所有重複都有停止條件與上限。廣播功能可透過目前通知路徑使用。

### S11｜安全 cursor、歷史分頁與串流升級

必讀：主規格第 7.3、8.1、8.2。

工作：

- NOTIFICATION_CHANGES、快照 cursor、一致排序與 /changes；涵蓋新增／read／ack／撤回／失效。
- 在所有 delivery 寫入交易內記錄 change。read path 的失效更新也需變更紀錄，不能悄悄改 DB。
- 定義提交後順序，不能以裸自增 id 假設 commit 順序；先在進度記錄序號／交易策略與故障案例，再實作。
- 歷史 pageToken 與增量 cursor 分開，超過100筆可查；保留 ids read，新增截至 cursor 批次模式。
- legacy event: inbox 保留；v2 SSE 有 id、變更事件、cursor 過期 resync。
- Web catch-all proxy 支援 Last-Event-ID／query；保持65秒預設 timeout 下的有界重連策略與授權。
- 新增 change log 不回播所有歷史聲音。

完成判定：提交交錯、連線重播／重設不漏變更，舊 UI 仍接收 inbox。可拆 S11-a「log/cursor」、S11-b「REST/SSE/proxy」，但接續需共享同一提交順序定義。

### S12｜前端同步與可恢復呈現

必讀：主規格第 3.3、3.4、7.2–7.4。

工作：

- capabilities 協商、snapshot＋cursor、分頁、重連／降級與恢復 SSE。
- 單主分頁訂閱與呈現，接手查共享 presentation 狀態；同時保持每個前景頁能讀收件匣。
- baseline 不重播個人歷史，但需確認廣播恢復；聲音最多待播3個、超量摘要、緊急優先。
- 401／登出清理 SSE、快取、播放資源與裝置狀態，避免帳號切換污染。
- 桌面權限、音效啟用、連線各自顯示；不支援時降級。
- Toast 6秒／懸停暫停、sticky、手機與鍵盤操作；非訂單 action 正確。

完成判定：與 S11 的 cursor 契約一致，主分頁接手不只依本頁記憶體判斷；過期／撤回變更更新所有畫面。

### S13｜音效生命週期與資產清單

必讀：主規格第 6。

工作：

- 沿用獨立 NOTIFICATION_SOUNDS／FILE_NAME、授權 content、FFprobe／FFmpeg。
- isActive／version／hash、軟刪除，規則及有效通知引用檢查；規則儲存與刪除的併發不能產生壞引用。
- 必須涵蓋個人規則、廣播規則、待發 payload、有效 delivery 的引用。
- 三個基礎 system code 不可刪；額外個人音效依授權管理，前端顯示引用衝突。
- 記錄真實三音檔、解析器可用性、存放／備份狀態；沒有檔案不宣稱已交付。
- 不遷移到 MEDIA_ASSETS，不讓圖片 cleanup 介入音效。

完成判定：程式生命週期完整，資產清單逐項有狀態。若只缺外部音檔，可記「程式完成／資產待交付」，S14 不得把整體發布標成就緒。

### S14｜整合與發布準備

必讀：主規格第 9.2 全部18條、第10節、進度檔所有未完成項。

工作：

- 將18條驗收案例映射到實際實作與證據；區分已核對／未執行／失敗／需要使用者驗證。
- 核對相容 migration 順序、資料不重播、flag 開關、capabilities、API／Web版本搭配。
- 完成允許的 build／靜態／artifact 檢查，修復本功能整合問題。
- 更新使用者說明目前可用能力、裝置限制與管理操作；移除已完成的「待擴充」，保留真實限制。
- 整理 API、Web 分別的發布及回退步驟、音檔與設定依賴；不以刪除資料回退。
- 根據已取得的發布授權才進行外部發布；沒有授權時交付可審閱的發布包與步驟。

完成判定：無未交代缺口；整體狀態可為「開發完成／待人工驗證或發布」，不能把未跑的案例寫成通過。正式發布是另一個狀態，不由本段自動觸發。

## 4. 每段驗證與發布界線

### 驗證

- S00：文件／路徑／契約核對。
- API 段：依實際 csproj／SDK 使用允許的 restore、build；沒有資料庫時 migration 僅做靜態檢查，不宣稱套用成功。
- Web 段：讀 package.json 採用實際 build 與允許靜態腳本；不能把含測試的聚合命令當成 typecheck 執行。
- 跨端段：API／Web 分別驗證，保留彼此版本；不要只因一端通過就標整段完成。
- 業務驗收用主規格案例作人工／程式追蹤清單；若本次使用者要求測試，再執行相應測試並記錄。不要把寫入正式訂單當成唯讀查核。
- dev 發布依 AGENTS 跳過所有自動化測試；不啟動 Playwright／瀏覽器測試。此限制不自動取消另行明確要求的 PR／正式測試。

### 發布

- 分段完成不自動 push、套 migration、啟用廣播或上傳正式音效。
- Web 任何程式／設定發布先 dev；使用者確認後才 dev → main 手動 PR，相同已驗證 commit。
- API dev 僅建置；API main 才發布正式，不把 Web dev 授權延伸成 API main。
- 新 Web 要依 capabilities 降級；API 能力尚未發布時，新選項不啟用。
- 遷移檔只增量新增、不修改已發布 migration；不由啟動自動套用。直接 SQL 帳號限制照 AGENTS／DATABASE-PERMISSIONS。
- 未完成能力用 flag／capability 隱藏，但不能長期把未完成工作以「已關閉」當成完成。
- 系統音效檔案、解析器或部署授權缺少時可先完成其餘程式，將外部依賴列在進度檔。

## 5. 中斷與接續規則

每完成一個小步就更新「目前接續點」，尤其是 migration 新增、接口改動、build 結果之後。交接至少包含：

- 段號及目前狀態、兩端 branch／HEAD。
- 修改的實際檔案與原因；已提交 commit 或未提交清單。
- 已完成／仍未完成；最後允許的驗證與結果。
- migration 是否僅建立檔案、是否已套用及證據。
- 當前接口決策、已知失敗、下一個最小動作。
- 有無背景命令仍執行；可恢復方式，不只給對話內 session id。

接續者先查實際 diff，再相信交接。若 token 突然用完沒有最後交接，以既有紀錄、未提交 diff 與局部 build 重建狀態；不要重置工作樹。

階段狀態只有：待開始、進行中、程式完成待驗證、已完成、受阻。外部資產／部署另列，不與階段完成混用。父段全部驗收滿足且證據記錄後才已完成。
