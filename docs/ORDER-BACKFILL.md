# 已成交訂單補登

店員可從原顧客、原營業日的後台訂單管理補登已實際成交的訂單。`open`、`closed` 與 `settled` 使用相同補登規則；補登不重開顧客點餐，不改變營業期狀態，也不授予店員重新結算權限。

## 輸入與資料保存

沿用管理端的 quote／submit 端點，在 `SubmitOrderRequest.backfill` 提供操作 UUID、實際發生時間、原因與預期帳款版本。必須先取得報價；一般顧客端拒絕所有帶有 `backfill` 的要求。原點餐碼可為 active 或 readonly，無須重新開放顧客點餐；其他失效狀態仍拒絕。

服務與包廂使用 `requestedStartsAt` 作為實際開始時間，`actualEndsAt` 必填，且開始、結束、實際交易時間都須在原營業期實際開店至關店範圍內，不可晚於現在。原營業期未關店時採最多 48 小時上限。購買節數與實際服務時間分開保存。

品項從現有菜單、店員服務與包廂選擇，預設顯示現行價格；店員須核對並可填入原成交價格：餐點／包廂 `unitPrice`，指名 `baseUnitPrice` 與 `serviceUnitPrice`。服務價覆寫為含加人費的原成交服務單價，原服務固定次數／按節計價規則仍適用。沒有憑空推算歷史價格或恢復已刪除的品項。

新訂單與履約項目直接為 completed，保存實際起訖、已完成數量、實際服務人員與 released 的歷史忙碌紀錄；不建立現在的等待佇列、接單通知、提醒或 active 忙碌區段。建立時間保留真實登記時間；`ORDER_BACKFILLS` 與訂單 audit 保存實際交易時間、原因、操作者及收款關聯。

## 帳款與防重

補登只建立應收，不自動新增實際收款。可以整筆關聯同一顧客已確認、未作廢、未歸屬且無分潤保留的收款；金額不得超過補登應收。跨單混合收款或已有退款的收款，請先透過帳款更正／作廢重登分開處理。已歸屬入場費、其他訂單或項目的收款不可被挪用。關聯保留原金額、收款營業期與時間，增加收款 revision 及帳戶版本。

若有同額的未歸屬 `charge_add`，阻擋補登並要求先核對原紀錄，避免訂單應收與加收應付重複。關聯收款已有 `tip_supplement` 且本單又含小費時也阻擋，避免重複分配薪資。

操作 UUID 與原始 payload 綁定；相同 UUID、相同內容重送回傳原訂單，即使報價已過期或帳款已更新。相同 UUID 不同內容回傳衝突。同一顧客、同一實際交易時間與相同品項／數量／服務時間再次使用新 UUID 送出也拒絕，訊息提供原單號。內容比對不受原因、價格預設值、品項排序、餐點拆行或時區表示差異影響。

營業期鎖、點餐碼／信物鎖、quote 消耗、內容防重、訂單及分項、稽核、收款關聯與帳款版本更新都在同一交易。任何錯誤整筆回滾。前端對網路或 5xx 等結果未明的提交保留原 UUID 與完整要求，只允許查回／重試同一筆。

## 結算銜接

尚未正式結算的試算會改回 draft 並增加輸入版本，避免舊試算直接正式結算。已正式結算的金額、來源快照與版本不變，overview 回傳 `pendingOrderBackfillCount`。只有原有經理權限可在最終步驟填原因並確認重新結算，沿用既有 V2、V3 與差額紀錄。

首次正式結算或確認重新結算時，在共用的營業期交易鎖內標記此次已涵蓋的補登；新補登仍為待重算，避免用時間戳猜測是否已計入。

## Migration 與驗證

發布依賴此功能的 API 前，依使用者指定的專案本機 DBA 流程套用 [20261020_02_order_backfills.sql](../db/migrations/20261020_02_order_backfills.sql)。本功能實作階段不修改正式資料。API 沒有獨立測試主機；Web 仍先 dev、驗收後再 main。

`dotnet run --project tests/OrderBackfill` 執行規則／內容防重檢查。加 `-- --integration` 時必須提供 `ORDER_BACKFILL_TEST_CONNECTION`，限定 127.0.0.1、非 3306 連接埠，以及尚不存在的 `codex_backfill_*` 測試資料庫。測試以不含資料的實際 schema fixture 建立本機資料表並重複套用新 migration，驗證並行重送、完成履約、現金總額、帳款 revision、語意防重、版本衝突回滾及結算保留。測試不讀取任何正式連線設定，也不刪除資料庫。
