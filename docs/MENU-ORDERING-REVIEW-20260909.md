## 2. 已確認缺口

| 項目 | 程式現況／影響 | 建議 |
|---|---|---|
| 消費規則新增 | 後台已有新增入口與 POST/PUT/DELETE API | 保留操作，擴充規則型態與欄位，無須另建第二套文字規則 |
| 規則欄位對應 | 標題、說明、價格文字都有前台對應；停用與排序由公開 API 篩選／排序 | 這部分基本一致；加預覽與欄位長度提示即可 |
| 規則與收費 | `PRICING_RULES` 僅文字；入場信物額度、指名基礎費、時間節數来自 ordering settings | 不從價格文字解析金額；建立明確資料來源連結 |
| 首頁收費 | 首頁讀 `shopInfo.pricing`，菜單讀 `pricingRules`，與 ordering settings 又是不同來源 | 首頁摘要引用選定規則，避免同一費用三處手動維護 |
| 舊價格備援 | 菜單先顯示打包快照；API 失敗時頁面未使用錯誤狀態提示。快照仍含 demo 文案與價格 | 加載入／更新失敗狀態、資料時間；點餐不得用靜態快照結帳 |
| 單品圖片／標籤 | 後台與公開 API 有圖片、tags；現行 MenuCatalog 單品列表未顯示，前台型別亦未包含這些資料 | 補圖片與標籤呈現；標籤改為可操作的輸入元件，避免直接編 JSON |
| 價格文字契約 | 前台單品型別及畫面讀 `priceText`，實際單品 API 契約只有數字 price | 統一契約，數字價格為計價來源；若需詢價品，另設正式定價模式，不能以 0 冒充未定價 |
| 套餐內容份數 | 後台／API 有 quantity，公開畫面只顯示角色與名稱 | 顯示「品項 × 份數」與中文角色 |
| 套餐角色 | UI 只有 main/dessert/drink；API 只限制字串長度 | 提供受控角色，按需要增加其他；角色只作內容分組，不決定通知或收費 |
| 套餐總開關 | API 讀 `menuSettings.showSets`，目前菜單後台沒有該入口；前台即使 sets 為空仍顯示「今夜套餐」區塊 | 補設定／清楚定義展示範圍；無套餐時隱藏區塊或給明確空狀態 |
| 套餐子品停售 | 公開查詢濾掉停售子品，卻仍回傳套餐與原價 | 不可默默少顯示內容；保存完整清單並回傳可售狀態與原因 |
| 分類與點餐不同步 | 公開單品查詢檢查分類啟用；提交訂單只按商品 ID 查本身供應狀態 | 統一 catalog 與提交的可售性判斷；舊購物車也必須重驗 |
| 套餐下單驗證 | 提交只查 MENU_SETS 本身，不核對組成品可售性；showSets 也未參與提交驗證 | 明確區分「隱藏展示」與「停售」；停售須在 API 擋下 |
| 套餐內容完整性 | 儲存服務沒有檢查非空組成、有效品項 ID、角色白名單等業務條件 | 補後端驗證；允許空草稿但不可上架空套餐 |
| 套餐歷史 | 訂單保存套餐名稱／價格／份數，未展開保存套餐子品 | 加內容快照，避免改套餐後無法還原訂購內容及香檳塔分類 |
| 後台套餐編輯 | 子品切換 ID 後仍保留舊 itemName；新增子品先加入主草稿，取消子視窗仍留下新增列 | 子編輯完成時才提交草稿；名稱依 ID 同步解析 |
| 儲存排序 | 現行逐筆重送整份菜單內容，含套餐內容重存；可部分成功，也可能覆蓋另一管理者變更 | 專用原子排序 API，只送 ID／順序，加版本衝突保護 |

## 3. 消費規則建議設計

保留 `/admin/menu` 的「消費規則」頁籤，每筆新增「僅說明」或「連結系統規則」模式。第一階段舊規則一律遷移為僅說明，不自動猜測低消、指名或包廂語意。

| 欄位組 | 建議內容 |
|---|---|
| 識別 | 穩定 id／code、版本、名稱、規則型態 |
| 展示 | 說明、排序、啟用、是否顯示於首頁／菜單／點餐確認 |
| 業務連結 | 對應信物額度、指名基礎費或其他已支援來源；不複製成另一個可獨立修改的金額 |
| 未來計價參數 | 金額、GIL 單位、每人／每次到店／每單／每節、適用單品／套餐／服務範圍 |
| 生效控制 | 生效時間、停用時間、優先序、是否可併用；顯示開關與計價啟用分開 |

建議第一期只支援「僅說明」與「已存在計價來源的連結」，尚未支援的類型明確顯示未啟用自動計價。自由文字仍可補充例外說明，但系統金額與單位由後端產生。

要接點餐計價時，由後端報價／提交共用同一判斷服務，回傳原價、可折抵金額、信物使用額、應付額與命中規則。最終提交核對規則版本及可售性；價格變更要請顧客重新確認，不能直接換價。

入場費、信物發放與低消是不同概念，須先确认是否金額相同、可否抵用、適用對象與收取時機。現行信物在開立 session 時確定，建議既有 session 保留原額度，避免調價回改已入場顧客。每筆訂單再快照當時適用規則與折抵結果。

若未來支援排除香檳塔折抵，須同步修改下單、改單重算、取消退款與報表；目前所有 menu_item／menu_set 都納入餐點折抵，不能只在 UI 移除勾選。

## 4. 香檳塔與通知 v1.1

### 分類責任

建議品項／套餐增加可多選的「事件分類」，第一個受控 code 為 `champagne_tower`。這是 v1.1 notification category 的可擴充實作提案；若使用陣列契約，須同步修訂通知文件。

- 一般菜單分類決定展示分頁；顯示標籤決定徽章；事件分類決定通知匹配。三者各自管理。
- 管理者明確勾選商品／套餐，不以名称包含「香檳」判斷，不猜正式商品 ID。
- 套餐有效事件分類 = 套餐自身分類與實際組成品分類的聯集。後台預覽「因包含哪個品項而繼承」；一般套餐預設不提供排除子品事件的開關。
- 訂單保存分類、來源子品與數量快照。套餐兩份、每份含三份相關品項，內容數量為六；不因主套餐與子品都標記而加算同一份內容。
- 如需要「塔數」而非「相關商品份數」，另設明確單位／換算欄位，不把所有 champagne_tower 分類商品一律當成一座塔。

### 事件流程

1. 後端驗證可售性與套餐內容，完成金額及內容快照。
2. 訂單和通知 outbox 寫在同一交易中；失敗不發事件。
3. 一張訂單只建立一次提交來源事件，payload 可含多個香檳塔品項及份數。
4. 通知中心匹配個人規則 8／香檳塔廣播模板；與一般點餐規則合併，同一收件人一張卡、依 v1.1 音效優先序播放。
5. 待協調訂單顯示「待店內確認」。讀通知、關閉提示、已知道與接單保持不同操作。

菜單設定只決定事件分類；收件人、聲音、重複次數、顯示方式維持在通知中心。如此未來可新增生日服務等分類，而不用在 MenuPage 增加個別播音程式。

**需確認的營運差異：**「香檳塔必須人工確認才製作」不是目前分類帶來的行為。若有需求，另外新增商品履約／確認政策並接訂單狀態，不以是否通知當作已接單。第一階段建議只增加分類與快照，維持既有接單語意。

## 5. 套餐與點餐選項

建議第一期維持固定套餐，明確呈現名稱、說明、價格、內容與各自份數。角色改顯示主餐／甜點／飲品／其他，空套餐不顯示成可購買商品。

可售狀態建議至少區分「上架」與「供應能力」。若要支援套餐專用品，另設「可單點」旗標，不能用停售代表只供套餐使用。必選內容缺貨時先採整組停售，後台列出原因；公開頁完整顯示內容及停售狀態或按展示政策隱藏整組，禁止只刪掉缺貨那一行。

點餐選項契約建議：

- 單點：分類、品項、價格、份數、可售狀態、可否信物折抵。
- 固定套餐：套餐份數、完整內容，內容數量隨套餐份數計算；明細只向顧客收套餐價，不再加收子品原價。
- 特殊商品：一般購物車行加事件／履約資訊即可，不必創建名稱特判的另一套購物車。
- 結帳確認：本次規則摘要、商品小計、可折抵範圍、信物使用／餘額、應付額與需要店內確認的提示。
- 下單成功：保存子品與分類快照，供店內出餐與通知使用；改名、停售、改套餐不回寫歷史。

如需「飲品三選一」，這是額外的自選套餐功能。須新增選項群組（至少／至多選幾項、允許品項、預設項、加價、份數限制），由前後端共同驗證。現有 itemRole 只是角色，無法表達單選／多選；不能以角色欄位冒充選項群組。

## 7. 驗收與發布邊界

- 人工案例涵蓋：新增／停用規則、首頁與菜單金額一致、API 失敗提示、套餐多份數、停售子品、隱藏分類的舊購物車、套餐修改後歷史不變、多項香檳塔一次事件、交易失敗不發通知。
- 批次 C 還須驗證：規則版本變更、信物折抵及退款一致、待確認語意、通知合併與音效優先序。此處列案例不代表已執行。
- Web 依專案規範先 dev；使用者確認後才能 dev → main。dev 預設只做建置、靜態／設定檢查、部署狀態與 HTTP 可用性，不跑自動化測試。
- API 沒有獨立測試主機，dev 僅建置；涉及新欄位的 Web 需相容舊 API／能力開關。API 正式部署與 migration 須另排發布時點，Web dev 不視為 API 正式發布授權。
