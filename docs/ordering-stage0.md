# 點餐流程階段 0

本階段建立跨日營業日、分項履約及獨立現場帳款基礎。現有營業日保留 `FLOW_VERSION=1`，新營業日在開店時明確選擇版本 2 才啟用新流程，不把舊應付金額回填為實收。

## 資料庫發布順序

依序套用 `db/migrations/20260914_01_operating_day_foundation.sql`、`20260914_02_order_fulfillment.sql`、`20260914_03_ordering_financial_records.sql`。皆為 MariaDB 新增式、可重複執行異動。先套用資料庫，再發布 API main，最後發布 Web dev。

2026-09-14 已套用三份異動。確認既有營業日沒有升版、可對應營業日的顧客關聯沒有遺漏、新帳款和履約資料表均沒有虛構歷史事件。回退應用程式時保留新資料表，不刪除營運紀錄；已開啟版本 2 的日子須繼續使用支援分項紀錄的 API。

## 契約與行為

- `IBusinessDayContext` 供點餐、公開店員資格、班表、工作身分及薪資日期使用。營業中以實際開啟的營業日為準；跨午夜不切成瀏覽器當天。測試日期覆寫保持原有功能。
- `GET/PUT /api/admin/business-day-plans/{date}` 保存每日完整開始、結束日期與版本。只有經理可改計畫。開店後原計畫不覆寫，另調整預計關店時間。計畫不自動開店。
- 手動開店保存實際開始、計畫快照、流程版本；預計關店過期必須明確指定新時間。關店與新單建立共用鎖，避免同時開兩個營業日或關店後才寫入新單。前日關店但未結算不阻止新日開店。
- `GET /api/admin/orders/{id}/fulfillment` 與 `POST /api/admin/orders/{id}/fulfillment/{unitId}/transition` 支援接單、開始、完成、取消未服務數量及指名改期。餐點可分數量；指名由本人或經理處理。舊整單與包廂入口不得覆寫版本 2 分項資料。
- 新分項訂單不因整單等待逾時被自動取消。取消只退回該項尚未服務的金額／餐點抵用額；原品項與原購入時數保留。訂單整體狀態由分項推導。
- `GET /api/admin/ordering-finance/sessions/{id}` 回傳應付、實收、實退、淨收、待收／待退及待確認。`POST .../records` 新增加收應付、折讓應付、實收或實退；`PUT .../records/{id}` 更正或確認。任何已登入店員皆可執行，無第二人核准限制。
- 原業務營業日、收退款營業日及實際發生時間分開；關店後仍可記錄和更正。未歸屬可先保存，金額立即計入現金淨額，分潤保留。更正保留修訂快照，不冒充另一次實際收退款。
- 新分項及帳款異動以操作編號、內容雜湊、版本與資料庫交易處理重送。費用操作可由 `.../operations/{operationId}` 查回；履約重送原操作回傳原結果。

## 後續階段界線

階段 0 尚未提供完整薪資計算與現金帳整合，因此版本 2 禁止沿用舊薪資計算／正式結算；未決款及分潤可保留。版本 1 維持原薪資流程。跨午夜自動打卡、人工出勤增減、完整延遲開工／休息協調及批次送餐工作台，仍按後續階段實作。超過指名預定開始的接單目前由分項改期入口處理，完整晚開始與折讓引導在階段 1。

## 本次驗證政策

依專案規定不執行自動化測試。本次驗證限建置、TypeScript／ESLint 靜態檢查、資料庫結構與關聯檢查、部署狀態及 HTTP 可用性；不代表已完成現場業務驗收。
