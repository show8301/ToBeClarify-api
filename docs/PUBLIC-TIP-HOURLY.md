# 公共小費：訂單實收與計薪工時

本文件取代 [舊小費訂單流程](ORDER-TIP-FLOW.md) 中的人頭均分及手動公共小費規則。

## 契約與來源

- 後台小費訂單分配支援 `public`、`designated`、`custom`。`public` 的 allocations 必須為空；訂單不鎖定員工名單，於結算依主要計薪職位工時分配。
- 舊 `equal` 快照保留可讀，但新建／更正不可再送 equal；回傳 `TIP_EQUAL_RETIRED`，需改選公共小費或正確的指定／自訂分配。
- 顧客與一般後台代客訂單沿用 staffId / staffPercentage 輸入。不指定、或指定比例為零時全額為公共小費；指定部分進個人小費，剩餘部分進公共小費。額外的 `PublicAmount` 保存在既有分配 JSON；不改歷史訂單。
- `ORDER_TIPS` 仍只有一筆訂單總額。分配 JSON 存在時，結算排除原始基礎列，由 loader 展開個人份額及一筆公共小費來源，避免重複認列。
- 不增加實收。依同一訂單已確認、未作廢、無保留的有效淨收款比例認列；退款扣減。沒有帳款紀錄時公共小費認列為零，不推定已收。
- 原 store portion 沒有分配 JSON 的歷史訂單維持原歸屬，列入 overview.publicTipPool.legacyStoreSources 核對；不能全資料庫自動轉成公共小費。

## 結算與快照

公式版本為 4；SaveCalculationCore 以實際 calculation.Run.CalculationVersion 保存，修正過去固定寫 2 造成的錯誤警告。

公共小費依指名人員／服務員／經理的主要職位計薪工時，按既有半小時等規則換算；幕後職位不參與，不因同人兼任增加第二份分配。活動日也使用計薪工時，與活動收入份額時數分開。

可分配整數金額為所有來源認列金額合計向下取整，未滿 1 G 部分顯示於認列總額但不發放。先以最大餘數分配個人總額，再平衡個人×訂單矩陣；以 staff ID、order ID 固定排序處理相同餘數。個人合計及來源訂單合計都必須守恆，不能逐人 ceiling 造成多發。小費不得再進公司收入或其他營收分潤池。

每個個人結果的 `public_tip` 來源保存訂單、原金額、認列基礎、收款、工時標籤、比例及整數分配。沿用既有 SOURCE_SNAPSHOT_ID，重算新增快照，舊快照保留；前台不用現在的出勤反推歷史工時。

有公共小費而合資格工時為零，產生 `PUBLIC_TIP_DENOMINATOR_ZERO` 阻擋正式結算。舊 equal／未作廢 tip_supplement 產生可連回訂單的核對異常；必須更正原訂單及作廢重複分配後重新預覽。

## 舊手動金額

輸入／重新結算請求保留 publicTipAmount 欄位以辨識舊 client，但只接受 0；新值一律由來源推導。公式版本小於 4 且既有 publicTipAmount > 0 時，需先補齊／核對訂單，填寫 publicTipReconciliationReason 後取代手動值。未解決的舊金額及版本會保留，不會因一次計算被誤標成已完成轉換。

未結算輸入保存記錄 public_tip_reconciled 稽核；已結算則透過既有經理預覽、原因、UUID、來源 token、版本及交易鎖機制建立新版，核對原因一併存入結算稽核。原結果與付款／追回紀錄保留。

## 驗證與發布

無新增資料表／欄位，不需要 migration；沿用已部署 ORDER_TIP_DISTRIBUTIONS JSON、結果來源及稽核表。此文件不代表已部署或已更正正式資料。

已設計的驗證入口：

- `dotnet run --project tests/SettlementRecalculation -c Release`：工時、退款、保留、無實收、尾差、活動日、舊資料核對及防重算版本。
- `dotnet run --project tests/OrderBackfill -c Release -- --integration`：必須先提供隔離本機 ORDER_BACKFILL_TEST_CONNECTION；程式只接受 loopback 非 3306、codex_backfill_* 新測試庫。驗證交易、防重、收款、更正及真實保存 SQL、來源歷史讀回。

本機現有套件還原會有 NuGet 弱點查詢連線警告及既有 ImageSharp 3.1.12 弱點警告；本次未更換套件。Web/API 建置與檢查結果須於交付時另行記錄。
